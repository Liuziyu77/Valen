# Qwen shared-state decisions

Set `model.qwen_execution` to `"shared_state"` to answer all questions in a record
with one Qwen backbone forward. The existing bilinear, MLP, role-MLP and mixer
candidate heads are retained; there is no LM head, answer-token prediction or
`generate()` call. Text, images and videos use the same processor path as before.

The default `"question"` mode preserves existing checkpoints and isolated Score
branches. A new training recipe is provided:

```bash
python -m valen.train --config configs/train/qwen/sft_shared_state.json
```

Copy this recipe and set `model.model_path`, `data.path`, `training.output` and
the step/epoch limits for your experiment. Existing JSONL records need no changes.
The recipe retains the synthetic-data smoke limits; it does not launch a full
video training run. Inference and evaluation recover the mode from the checkpoint.

## Sequence and scoring

Each record is compiled as:

```text
[state messages, including media, once]
user:
  Question 1: task, instruction, candidates
  Question 2: task, instruction, candidates
  ...
assistant:
  Question 1 Decision:
  Question 2 Decision:
  ...
```

The numeric question positions are generated by the compiler. External question
IDs, group IDs, labels and metadata never enter the prompt. Every decision
position sees the complete question schema under ordinary causal attention.
Earlier readout text contains no predicted or gold answers. Candidate endpoint
positions and role spans select the existing head inputs from one hidden tensor.

Score produces all K candidate logits from this same forward, without K separate
backbone branches. Grade IDs remain absent from the Score candidate text, but all
grade descriptions are visible. This changes the old Score isolation semantics.
Question/option order and the presence of other questions can affect predictions;
this mode is not numerically equivalent to the legacy independent prompts.
Changing candidate order also changes causal representations before the head.

## Training and budgets

One backend training unit owns all question logits and their shared graph. The
runner combines their losses and calls backward once for that state, retaining
the existing per-video/per-question weighting. Soft target distributions, SFT
cross-entropy, Brier and Score RPS are unchanged. No shared features are detached
in ordinary training, so gradients reach any trainable backbone components.

`logical_tokens` and `compute_tokens` both equal the actual shared sequence length.
`max_length` now caps the complete state plus all questions/readouts.
`tokens_per_step` still packs complete records per rank. Overlong records fail
explicitly; automatic question splitting is not implemented. Shared activations
live until the combined backward, so memory and throughput should be measured
with the intended frame count, resolution and number of questions.

RLCD also uses a shared forward for each policy/reference evaluation and each
uncached update. Its optional frozen-feature cache stores per-question readouts
from one shared backbone execution; the existing first-use consistency check adds
one extra forward. Gradient checkpointing can recompute layers during backward.

The mode is saved in checkpoint config and run-manifest adaptation metadata.
`--resume` rejects mode changes; `--initialize` can start a new experiment in the
other mode with compatible weights. Such a transition needs training/evaluation,
not an assumption that existing quality or calibration remains unchanged.

## Validation

`tests/qwen/test_shared_state.py` checks position/label alignment, media tensor
reuse with a mocked processor (no video decoding), one-forward execution,
shared-backbone gradients against repeated execution of the **same new sequence**,
all four heads, mixed task types, cached RLCD, and SFT checkpoint/resume.
Tiny randomly initialized Qwen3.5 tests additionally cover full attention,
DeltaNet, gradient checkpointing and synthetic video patches on CPU, including
gradient flow into the visual tower. They load no pretrained weights or video files.
It does not assert equivalence to legacy prompts or claim a GPU speedup.

Evaluate task quality and question-order sensitivity on held-out data before
adopting this mode for a trained deployment. GPU throughput and full video-data
training are separate from these correctness tests.
